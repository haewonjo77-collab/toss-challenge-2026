# 6명이 회의 일정을 잡는 경험 설계

> 회의 조율의 병목은 빈 시간을 모으는 속도가 아니라, 이 시간이 확정 가능한지 판단할 근거가 부족한 데 있었다.

- 프로토타입: https://toss-challenge-2026.netlify.app
- GitHub: https://github.com/haewonjo77-collab/toss-challenge-2026
- 형태: 모바일 중심 웹 프로토타입
- 기술: React, TypeScript, Vite
- 주요 진입점:
```
- `/`: 주최자 회의 생성 플로우
- `/join`: 참석자 응답 플로우
```
## 문제 정의

7명을 대상으로 한 UT와 3번의 개선 사이클에서 가장 크게 드러난 문제는 “빈 시간을 모으는 속도”가 아니라 “확정 가능한 시간인지 판단할 근거 부족”이었다.

첫 UT에서 주최자 플로우는 3분 12초, 참석자 플로우는 2분 20초가 걸렸다. 사용자는 입력 자체보다 판단 지점에서 멈췄다. 기존 캘린더와 일정 서비스 5개를 직접 써보니 대부분 응답을 모으는 발산 과정은 제공하지만, 모인 후보를 최종 결정으로 수렴시키는 과정은 여전히 사용자의 몫이었다.

참석자는 보통 “외근”, “점심 직후 회피”, “기존 회의”처럼 피해야 할 시간을 먼저 떠올린다. 하지만 기존 입력 방식은 가능한 시간을 계산한 뒤 칸 단위로 선택해야 해서 사용자가 두 번 생각해야 했다. 주최자도 후보를 받은 뒤 필수 참석자, 선택 참석자, 미응답자의 무게를 다시 계산해야 했다.

그래서 문제를 단순한 일정 입력 문제가 아니라 **확정 판단의 수렴 실패**로 다시 정의했다.

## 해결 방향

핵심 가설은 “가장 많은 사람이 되는 시간”이 아니라 **가장 적은 조정으로 확정할 수 있는 시간**을 추천해야 한다는 것이다.

| 가설 | 문제 | 해결 |
| --- | --- | --- |
| A. 응답 현황 공개 | 누가 응답했는지 몰라 확정이 늦어진다 | 오픈폴 구조로 응답 상태와 미응답자를 같은 화면에 노출 |
| B. 안 되는 시간 입력 | 가능한 시간을 고르는 과정이 부담스럽다 | 참석자는 안 되는 시간만 표시하고, 사내 일정은 자동 반영 |
| C. 필수/선택 기반 추천 | 인원수 중심 후보가 맞는 답처럼 보인다 | 필수 참석자 전원 가능을 1순위로 두고, 선택 참석자 손실을 최소화 |

이 중 C를 핵심 판단 로직으로 두고, A와 B는 C가 잘 작동하도록 돕는 보조 장치로 설계했다.

## 프로토타입 흐름

### 1. 주최자: 회의 만들기

주최자는 회의 제목, 후보 날짜, 가능 시간대, 회의 길이, 참석자를 정한다. 참석자는 조직 멤버 검색으로 추가하며, 각 사람을 필수 또는 선택 참석자로 지정할 수 있다.

필수/선택은 단순 배지가 아니라 이후 추천 로직의 기준이 된다. 새 참석자는 기본적으로 필수로 추가되어, 반드시 필요한 사람을 놓치는 위험을 줄였다.

### 2. 참석자: 안 되는 시간만 표시하기

참석자는 가능한 시간을 고르는 대신 안 되는 시간만 누른다. 사내 일정은 이미 반영된 상태로 보여주고, 필요한 경우 Google, Kakao, Apple 캘린더를 추가로 불러오는 흐름을 넣었다.

시간은 하루 단위 아코디언으로 나눠 보여준다. 모든 날짜와 슬롯을 한 번에 검수하게 하지 않고, 사용자가 사건이나 일정 구간 단위로 빠르게 판단할 수 있게 했다.

### 3. 대기 화면: 응답 현황과 알림

주최자는 누가 응답했고 누가 아직 남았는지 바로 확인한다. 필수 참석자가 모두 응답하기 전에는 추천 시간을 볼 수 없고, 미응답자에게 알림을 보낼 수 있다.

선택 참석자가 아직 응답하지 않은 경우에도 필수 참석자가 모두 응답했다면 추천 확인으로 넘어갈 수 있다. 단, 미응답자를 가능한 사람으로 계산하지 않는다.

### 4. 추천 화면: 확정 가능한 후보만 보여주기

추천은 다음 순서로 계산된다.

1. 필수 참석자가 모두 가능한 후보만 먼저 남긴다.
2. 그 안에서 선택 참석자의 가능/일부 가능/불가 상태를 점수화해 정렬한다.
3. 전원 확정 가능한 시간이 있으면 추천 하나만 보여준다.
4. 필수 전원이 겹치는 시간이 없을 때만 대안을 보여주고, 빠지는 필수 참석자를 명확히 드러낸다.

선택 참석자는 기본적으로 접어 두어 확정 판단의 노이즈를 줄였다. 사용자는 “이 시간이 왜 추천됐는지”와 “누구에게 양보를 요청해야 하는지”를 한 화면에서 판단할 수 있다.

### 5. 확정 화면

후보를 선택하면 별도 재확인 단계 없이 회의 시간이 확정된다. 확정 후에는 참석자에게 알림을 보냈다는 상태와 필수/선택 참석자의 가능 여부 요약을 보여준다.

## 검증 결과

| 항목 | 첫 UT | 마지막 UT | 변화 |
| --- | ---: | ---: | ---: |
| 주최자 플로우 | 3분 12초 | 45초 | 약 4.3배 단축 |
| 참석자 플로우 | 2분 20초 | 23초 | 약 6.1배 단축 |

속도 개선보다 중요한 변화는 사용자가 다시 확인하는 장면이 줄었다는 점이다. 입력을 빠르게 만드는 데서 멈추지 않고, 주최자가 믿고 확정할 수 있는 근거를 추천 화면에 담는 방향으로 개선했다.

## 왜 이 방식인가

회의 조율의 본질은 “가장 많은 사람이 되는 시간”을 찾는 일이 아니라 “가장 적은 조정으로 모두가 납득할 수 있는 확정안을 만드는 일”이라고 보았다.

고민한 대안은 전원 응답 후에만 추천을 보여주는 방식, 인원수 기준으로 후보를 정렬하는 방식, 로그인 없이 링크 하나로 끝내는 방식이었다. 하지만 UT에서 주최자는 모두가 응답할 때까지 기다리기보다, 필수 참석자가 모두 가능한 상태에서 선택 참석자의 손실을 최소화한 결정 가능한 추천안을 원했다.

그래서 필수/선택은 시각적 표시가 아니라 추천의 기준으로 반영했다. 회사 안에서 반복되는 회의 조율이라는 맥락을 고려해 조직 멤버 검색과 사내 일정 반영을 전제로 했고, 완전한 캘린더 앱이나 조직도 관리 대신 응답 수집, 가중치 판단, 확정 추천의 핵심 흐름에 집중했다.

설계의 목표는 더 많은 선택지가 아니라 **더 적은 망설임**이었다.
